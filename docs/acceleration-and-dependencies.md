# Acceleration and dependency decisions

The release remains RapidOCR 3.9.2 with ONNX Runtime 1.30.0 CPU inference. Qt/PySide6 Essentials 6.12.0, Pillow 12.3.0, MSS 10.2.0, HTTPX 0.28.1, keyring 25.7.0 and packaging 26.3 match the reviewed current upstream versions. All transitive Windows artifacts remain hash-pinned. The complete lock is audited separately for known vulnerabilities.

RapidOCR 3.10.0 was published October 8–9 and ONNX Runtime 1.31.0 on October 9, immediately before this pass. [RapidOCR's release notes](https://rapidai.github.io/RapidOCRDocs/main/changelog/v3.10.0/) change routing/lazy loading, model metadata and OpenCV's default to headless. Its Torch-specific safe-loading changes do not apply to our shipped ONNX-only path. [ONNX Runtime's notes](https://github.com/microsoft/onnxruntime/releases/tag/v1.31.0) cover model/package and provider-selection APIs. We retain the already qualified versions rather than refreshing the native runtime/lock without a complete packaging and quality comparison. No claim is made that these older pins are universally preferable; re-evaluate before stable if qualification dates move.

The official [DirectML Python distribution](https://pypi.org/project/onnxruntime-directml/) is 1.24.4, not a matching 1.30.0 wheel. An isolated environment with the official hash-verified wheel ran authored Japanese/Korean/English fixtures with actual `DmlExecutionProvider` sessions; all three were exact after whitespace normalization. Warm medians were 587/555/559 ms. The shipped CPU runtime measured 1,152/1,060/1,076 ms on those fixtures during this workload. These are different runtime versions on one loaded dual-GPU host, not a controlled universal speedup claim. CPU 1.24.4 also measured approximately 1,098/1,114/1,133 ms. See the raw CPU/DirectML investigation JSON and `tools/investigate_acceleration.py`.

The benchmark requested DXGI adapter index zero; it does not claim which vendor adapter Windows selected. It needed a RapidOCR provider-option conversion plus DirectML sequential execution/memory-pattern constraints. [ONNX DirectML guidance](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html) describes those constraints and sustained-engineering status. [Windows ML's newer provider path](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/supported-execution-providers) has a different Windows version/runtime qualification matrix. Before a user-facing acceleration option, validate fresh packaging, explicit provider verification, device loss/recovery, memory over hours and more than one vendor/device. The primary environment and release lock were not replaced by the experiment. CPU is the honest compatibility default.

The implemented window backend uses physical client rectangles and normalized crops over MSS, with conservative visibility/identity checks. [Windows Graphics Capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) requires WinRT/D3D frame-pool, resizing/device-loss and format/HDR handling. There is no qualified Python/native bridge or packaged WGC backend in this release. It remains a useful V2.x investigation; the current backend explicitly waits while covered/minimized and does not promise protected or exclusive-fullscreen capture.

Universal script routing is also deferred. Source selection deterministically chooses managed recognition families; Auto explicitly describes its Chinese/Latin limits. Recent upstream multilingual routing does not establish its quality on games/subtitles. Spanish, English, Japanese, Korean and both Chinese sample families have retained recognition evidence; other advertised language families still need dedicated corpus/manual coverage.
